# Upload via presigned URL and MinIO bucket notification

Issue #7 originally specified that the Next.js upload route would receive the image bytes, write them to MinIO, create the `receipts` row, and send the extraction event. Instead, the server issues a short-lived presigned URL to the browser, the browser uploads the image directly to MinIO, and MinIO notifies the server via a bucket-notification webhook. The upload route creates the row up front with status `uploading`; the webhook handler then promotes the row to `pending` and triggers the Inngest extraction workflow.

We chose this because it keeps S3-compatible credentials out of the browser, removes large image payloads from the Next.js server, and still lets the server control the object key, the database row, and the returned `receiptId`. The trade-off is extra infrastructure coupling: MinIO must be able to reach the webhook route, and the upload flow is split across two network hops plus an asynchronous event. We deliberately kept only one upload-phase status (`uploading`) and no `upload_failed` state; a failed upload is retried from the same `uploading` row. The browser learns that the upload succeeded from MinIO's HTTP response, shows an immediate confirmation, then navigates to `/receipts` via Next.js client-side navigation so the server-rendered list fetches fresh data without a full page refresh.
