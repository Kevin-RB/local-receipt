# ADR-0013: Test fixtures are curated and opt-in; demo data stays in `receipts_seed`

Date: 2026-10-17

## Status

Accepted.

## Context

ADR-0004 draws a deliberate boundary: `pnpm db:seed` generates plausible-but-fake demo data into a dedicated `receipts_seed` database, and the real `receipts` database is never touched by it. That boundary exists so a seed can reset and re-derive without risking scanned receipts.

The boundary also left the app database with no fixture path. Verifying the chat end to end — the tables the tools render, their totals, the model's prose — needs a signed-in account with a realistic spread of receipts. An agent could not get one: the demo user has no Better Auth `account` row and therefore cannot sign in, and the demo rows' columns are drawn independently, so line items do not reconcile with receipt totals. Every attempt repeated the same manual work — sign up through the UI, copy receipts between accounts, then clean up.

Two needs are being served and they are not the same:

- **Demo data** is for looking at the app. It is expendable, reset-and-reseeded, and does not need to be coherent or sign-in-able.
- **Test fixtures** are for driving the app. They must be sign-in-able, deterministic, idempotent, arithmetically coherent, and safe to add to an account that also holds real receipts.

## Decision

Keep ADR-0004 intact and add a second, explicitly separate path: **`pnpm db:fixture`**, implemented in `scripts/db-fixture.ts` with the data generated by the pure function in `lib/db/fixture.ts`.

- **Demo data**: `pnpm db:seed` → `receipts_seed`, reset-and-reseed, independent generators, not sign-in-able. Unchanged.
- **Test fixture**: `pnpm db:fixture --email <address> --apply` → the app database named by `DATABASE_URL`, opt-in, development only.

The fixture's guarantees:

1. **Sign-in works.** It creates the Better Auth `credential` account row the seed omits, hashing the password with `better-auth/crypto`'s `hashPassword` — the same function the sign-up path uses — and matching what the sign-up path writes: `providerId` `credential` with the user id as `accountId`, which is all Better Auth 1.7.3+ uses to recognise the account. The credentials are printed. It bypasses the invite-code gate because it never calls the sign-up endpoint; that is intentional for a development fixture. The canonical agent account is `trace-test@example.com` with the fixed `FIXTURE_PASSWORD`, and it is the command's default target. On every apply the canonical account's stored hash is verified against that password and reset only when it does not match, so the documented credentials always sign in without making a matching re-run write anything. No other account's password is ever reset.
2. **Deterministic.** A fixed PRNG seed, deterministic UUIDs namespaced by email, and a runner-supplied anchor date. Two runs with the same inputs produce identical fixture data and identical receipt ids; the account and line-item row ids the database assigns are outside that contract. Dates are anchored to the run date (the trailing twelve months) rather than a hard-coded calendar date so the chat's "this year" questions always have data; tests pass a fixed `asOf`.
3. **Idempotent and non-destructive.** Deterministic ids plus `ON CONFLICT DO NOTHING` mean a second run inserts nothing, even on a later day when the dates have moved. Receipts belonging to another owner are never read into, updated, or deleted. The command refuses to add fixture rows to an account that already has receipts of its own unless `--force` is passed, and even then it only inserts its own rows. The owner account (`kr38996@gmail.com`) therefore needs `--force`; a fresh agent account does not.
4. **Coherent.** Line items are the source of truth: product lines are unit price × quantity, surcharges add, discounts subtract, and the receipt total is their sum. One receipt deliberately misses its total and carries `hasIntegrityWarning`, so the warning path is exercised rather than silently absent. Subtotal and GST appear on half the receipts and are null on the rest, matching ADR-0007's "stored only when the receipt prints it" rule: on the receipts that print them, the fixture authors the values a printer would (product lines' sum, and the inclusive GST component of the total).
5. **The corpus exercises every chat tool.** Three receipts per month for twelve months, ten merchants with repeat visits, line items across 20+ leaf categories, uncategorised items, a surcharge, a discount, all payment methods, and one receipt with no merchant.
6. **Targeting is explicit.** A dry run is the default; `--apply` writes. `--email` defaults to the agent test account (`trace-test@example.com`), so the command an agent reaches for provisions that account and not the owner's; naming another email is an explicit choice, and the owner's needs `--force`. The command refuses `NODE_ENV=production`, and also refuses an unset `NODE_ENV` — a deployed container such as the `toolbox` sets neither, so "not production" alone is not a safe signal. The target is `DATABASE_URL`; `SEED_DATABASE_URL` is not consulted, so the two paths cannot be confused.
7. **Images are intentionally absent.** Fixture receipts have a null `object_key`. Writing placeholder objects would make the command depend on RustFS, and the point of the fixture is that it works with Postgres alone. The receipt image route returns 404 and the detail page renders its "No image available" state; links from chat still land on the receipt's data.

## Consequences

- `AGENTS.md` names the fixture account as the one every browser check signs in with, and gives `pnpm db:fixture --apply` as the idempotent way to ensure it exists. That is the convention the next agent follows; the default `--email` is what makes the simple command safe.
- Running the fixture against an account with real receipts requires `--force`, and the command says so rather than doing it silently. The owner account and any account that already has its own receipts take this path; their existing password is not reset — only the canonical fixture account's password is repaired when it has drifted, because those credentials are part of the fixture's contract.
- The fixture is not reset by `pnpm db:seed` and is not removed by it: it lives in the app database, which the seed never opens.
- Fixture rows carry recognisable receipt numbers (`FIXTURE-1` …) and deterministic ids, so they can be identified and deleted without matching on amounts.
- Categories come from the migration-seeded taxonomy. The command fails with an explicit message if a slug is missing, which is the same signal that `pnpm db:migrate` has not run.
- The anchor date moves from day to day, so a fresh run on a later day dates the corpus differently. Ids do not move (they hash the seed, email and name), which is what keeps the second run a no-op; determinism of the data itself is asserted at the generator seam with an explicit `asOf`, not against a fixed wall clock.
- CI does not run the fixture: it needs neither RustFS nor LM Studio, but it does need a migrated Postgres, which the unit suite deliberately does not require. The DB-writing half lives in `lib/db/fixture-provision.ts` with an optional Postgres-backed integration test behind `FIXTURE_TEST_DATABASE_URL`; `pnpm test` skips it, and it refuses a database whose name does not contain `test` or `fixture`.
